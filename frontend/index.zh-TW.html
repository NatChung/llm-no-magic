⑦ 選型 — 能 Skill 就先 Skill

      
要提供服務給別人時,該做成 Skill 還是 MCP?

    

    

      

        
結論

        
能 Skill 就先 Skill。MCP 是被條件逼出來的升級,不是更進階的選擇。

      

      

        
分析 — 為什麼 Skill 先行

        

          
1. Skill 反正都要寫,先寫永遠不白費

          
「怎麼用得對」—— 順序、格式、邊界、什麼時候別用 —— MCP 協定裡沒有欄位放,只能寫在 Skill。所以 Skill 是兩條路共同的必交作業;之後真要升級 MCP,只是把資料搬出去,不是打掉重練。

        

        

          
2. Flow 的修理權在我手上

          
Skill 是我寫的流程文件,MCP 是給一疊工具卡、順序由模型當場決定。要誠實:SKILL.md 也只是給模型看的指示,兩邊都擋不住模型即興;MCP 甚至在「單一呼叫」層更確定(typed schema、server 可測試)。真正的差別在出錯之後:Skill 的流程錯了,改文件即生效;MCP 的編排錯了,沒有文件可改 —— 你只能換模型或加 prompt。修理成本,才是服務品質可重現的關鍵。

        

        

          
3. 零維運

          
Skill 是檔案,交付即結束;MCP 是 server,從部署那一秒起就要 24/7 養著它。

        

      

      

        
例外 — 任一成立才上 MCP

        
    
          
  • 資料不能落在對方手上 — Skill 裡寫的權限檢查只是「給模型看的指示」,擋不住人;要真授權、撤銷、分級,只有 hosted 一條路
    • 
          
  • 對方的 client 跑不了腳本 — claude.ai/Cowork 預設打不出 HTTP、別家 client 讀不懂 SKILL.md
    • 
          
  • 資料必須 live — Skill 的資料是打包當下的 snapshot
    • 
        

      

      

        
Security 注意

        
Skill 本質是「在對方機器上跑你給的腳本」—— 對方裝你的 Skill,跟裝瀏覽器外掛是同一種信任判斷。企業環境常因為治理(governance)理由反而偏好 MCP 的集中管控:工具在 server 端、行為可稽核、權限可收回。這是例外一的另一面,對聽眾裡的資安背景要主動講。

      

      
而且被逼上 MCP 之後,Skill 也不退場 —— 它瘦身成規矩層,繼續管「怎麼用得對」。MCP 給能力,Skill 給規矩。
